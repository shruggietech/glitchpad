# v0.1.4 Release Operator Runbook

## Stable Android authority

Reuse the existing project-owned RSA 3072-bit Android keystore and its recovery material. Do not generate a replacement key. Confirm that repository secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`, and `ANDROID_SIGNING_CERT_SHA256` remain configured without printing their contents. The expected fingerprint remains the existing uppercase colon-separated SHA-256 certificate fingerprint.

## Publication ritual

1. Confirm the v0.1.4 release pull request is merged, every required check is green, and local `main` matches the reviewed v0.1.4 merge commit. The source includes S039, S040, the AppFrame adoption, the formal S042 BrandBuilder kit, and accepted compatible dependency updates.
2. Confirm the stable Android keystore recovery copy is accessible outside the repository.
3. Manually dispatch the `release` workflow from current `main` and require `Validate release preparation` to pass. This checks committed evidence and all five Android authority values without printing them and cannot publish.
4. Confirm no local tag, remote tag, or GitHub release named `v0.1.4` exists, preserve the historical v0.1.3 release, and add the exact `v0.1.4` tag to the protected `github-pages` environment deployment policy.
5. Create the annotated tag `v0.1.4` on the reviewed v0.1.4 merge commit and push only that tag.
6. Watch the Windows, macOS, Linux, Android, and release workflows. Any missing package, failed required gate, stale identity, practical-use evidence mismatch, or Android fingerprint mismatch stops publication. Preserve non-gating performance misses in evidence and release notes.
7. Confirm the GitHub release contains exactly eight application packages, four evidence bundles, `SHA256SUMS`, and `community-release-manifest.json`.
8. Confirm every package and evidence record names v0.1.4 and the reviewed source revision, desktop practical-use receipts bind to the final manifests, and the release-authorized site deployment succeeds only after the GitHub release exists. Record publication and continue manual real-world validation under #66.

The release workflow refuses to replace an existing v0.1.4 release. Manual workflow dispatch validates readiness only; publication remains restricted to the exact annotated `v0.1.4` tag. If only the post-release site handoff fails, dispatch the `docs` workflow with `deploy=true` and `release_tag=v0.1.4`; it checks out that tag and refuses deployment unless a non-draft v0.1.4 GitHub release exists at the same commit.
